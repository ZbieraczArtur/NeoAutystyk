Wprowadź poniższe zmiany w istniejącym programie. Nie przebudowuj całej aplikacji od zera i nie zmieniaj istniejącej logiki, która nie jest bezpośrednio związana z opisanymi poniżej zmianami. Najpierw przeanalizuj obecną implementację, sposób działania manifestu, systemu odpowiedzi, requires, wartości for/against, profili oraz popupów. PRIORYTET 1 — POPRAWNA LOGIKA NEITHER

Zmodyfikuj sposób działania odpowiedzi Neither.

1. Automatyczne Neither dla pytań ukrytych
Każda teza, która jest obecnie ukryta z powodu niespełnionych warunków requires, musi automatycznie posiadać odpowiedź Neither.

Przykład:

{
  "id": 5,
  "require_yes": [75],
  "require_no": [44]
}

Jeżeli warunki nie zostały spełnione, pytanie 5 jest ukryte, ale jego stan odpowiedzi powinien być traktowany jako:
Neither
Nie oznacza to jednak, że ukryte pytanie ma być traktowane tak samo jak aktywnie wybrane Neither pod względem interfejsu — chodzi o zachowanie poprawnego stanu logicznego i wartości.
2. Neither NIE daje values_for ani values_against
Jeżeli użytkownik wybierze Neither, nie może otrzymać żadnych punktów for ani against z tej odpowiedzi.

Czyli:
Neither → values_for = 0
Neither → values_against = 0
Neither powinno przekazywać wyłącznie wartości przypisane do odpowiednich profili z expoertcode, np.:
partii,
użytkowników,
figur politycznych,
ideologii,
innych encji,
jeżeli obecna architektura programu wykorzystuje takie wartości.
To chyba już mniej więcej istnieje, ale mogą być wymagane poprawki

3. Wyjątek: tryb deweloperski
W trybie deweloperskim chcę mieć możliwość ręcznego zaznaczenia innej odpowiedzi dla pytania, które normalnie jest ukryte i automatycznie ma Neither.
Przykład:
Pytanie jest ukryte:
Neither = aktywne automatycznie
W trybie deweloperskim mogę dodatkowo zaznaczyć:
Zdecydowanie się nie zgadzam
Wtedy obie odpowiedzi pozostają zaznaczone:
☑ Neither
☑ Zdecydowanie się nie zgadzam
Jest to celowe zachowanie trybu deweloperskiego i nie powinno być automatycznie uznawane za błąd.

4. Punktacja w takim przypadku
Jeżeli Neither pozostaje zaznaczone i jednocześnie deweloper ręcznie zaznaczy inną odpowiedź, odpowiedź Neither:
nie daje values_for,
nie daje values_against,
daje +1 punkt w odpowiednim liczniku związanym z Neither.

Jeżeli dodatkowo zaznaczona jest odpowiedź:
Zdecydowanie się nie zgadzam
to również przyznawany jest +1 punkt zgodnie z obecnym systemem punktacji tej odpowiedzi.
Pozostałe odpowiedzi, z wyjątkiem Pomiń, zachowują obecny sposób naliczania punktów ujemnych.

5. Nie zmieniaj znaczenia pozostałych odpowiedzi
Nieither ma być specjalnym stanem automatyczny stan pytania nieaktywnego - ale wciśnięcie go szybko 3 razy powinno go wyłączyć w danym pytaniu - powinien wtedy zmienić barwę by komunikować nieaktywność.
Nie należy zmieniać obecnej punktacji pozostałych odpowiedzi poza sytuacjami opisanymi powyżej.

PRIORYTET 2 — NAPRAWA PYTAŃ DYNAMICZNYCH / REQUIRES
Ostatnie zmiany spowodowały problemy z działaniem tez warunkowych. Napraw cały system dynamicznego ujawniania pytań.
Podstawowa zasada
Jeżeli teza znajduje się w manifest.json i posiada wymagania requires, to początkowo jest ukryta.
Przykład:
{
  "id": 5,
  "require_yes": [75],
  "require_no": [44]
}
Oznacza to:
Pytanie 5:
- początkowo ukryte,
- pojawia się dopiero, i od razu po spełnieniu wszystkich odpowiednich warunków, jeśli jest więcej to powinny być obok siebie,
- po pojawieniu się staje się normalnie widoczne i odpowiadalne.
Ważne
Warunki muszą być sprawdzane dynamicznie podczas korzystania z testu.
Jeżeli użytkownik zmieni odpowiedź na pytanie będące warunkiem, system musi natychmiast ponownie obliczyć zależności.
Przykładowo:
Pytanie 75 → zmiana odpowiedzi
        ↓
ponowne sprawdzenie requires
        ↓
Pytanie 5 → pokazuje się / ukrywa
Nie może być sytuacji, w której pytanie pozostaje widoczne lub niewidoczne mimo zmiany odpowiedzi spełniającej warunek.

PRIORYTET 3 — NOWY SYSTEM OR W REQUIRES

Rozszerz system wymagań o możliwość definiowania alternatywnych warunków OR.

Obecnie mamy np.:
{
  "id": 84,
  "require_yes": [101],
  "require_no": []
}

Chcę możliwość zapisania:

{
  "id": 84,
  "require_yes": [
    [101],
    [73]
  ],
  "require_no": []
}

co oznacza:
101 LUB 73

Jeszcze bardziej złożony przypadek:
{
  "id": 84,
  "require_yes": [
    [101],
    [73, 25]
  ],
  "require_no": []
}
oznacza:

101 LUB (73 I 25)

Czyli:
grupa [101] = jeden warunek,
grupa [73, 25] = oba warunki muszą być spełnione,
pomiędzy grupami występuje OR.
Wszystkie istniejące requires należy ujednolicić

Obecny system:
"require_yes": [101, 73, 25]
powinien zostać logicznie potraktowany jako:
101 AND 73 AND 25
Natomiast nowa struktura pozwala wyrazić:
101 OR 73 OR (73 AND 101 AND 25)
System powinien więc rozróżniać:

warunki wewnątrz grupy = AND
grupy = OR

Przy zachowaniu kompatybilności możesz obsługiwać również starą składnię, jeżeli jest ona już używana w istniejących danych.

require_no

Analogiczny mechanizm powinien działać dla require_no.

PRIORYTET 4 — WIZUALNE OZNACZENIE PYTAŃ AKTYWOWANYCH

Tezy, które zostały ujawnione dzięki spełnieniu warunków requires, powinny być wizualnie odróżnione od zwykłych pytań.
Obecnie pytania posiadają po lewej stronie kolorowy:
left accent border,
side indicator bar
lub podobny element - nie potrafię tego nazwać.

Nie zmieniaj całego komponentu.
Chcę jedynie, aby pytania aktywowane dynamicznie otrzymały inny kolor tego lewego paska.
Obecny stan
Zwykłe pytanie:
niebiesko-zielony gradient
Nowy stan
Pytanie aktywowane przez requires:
żółto-czerwony gradient
Powinno być jasne wizualnie, że jest to pytanie dodatkowe / warunkowe.

Nie zmieniaj koloru wszystkich pytań — tylko tych, które zostały aktywowane przez system dynamiczny.

Na stronie startowej, podczas przeglądania listy pytań, dodaj możliwość sortowania tez według ID.
Dodaj opcję:
Sortuj:
- domyślna kolejność
- ID rosnąco

Przykład:
ID 1
ID 2

ID 4
...

Na końcu tabeli, poza właściwą listą pytań, pokaż panel diagnostyczny informujący o brakujących ID.

Przykład:

ID 45 → ID 46 → ID 48

Jeżeli występuje więcej brakujących ID, pokaż wszystkie.

Sprawdzenie bazy tez

System powinien dodatkowo sprawdzić, czy brakujące ID:

To ma być narzędzie diagnostyczne dla dewelopera, a nie element normalnego widoku użytkownika.
